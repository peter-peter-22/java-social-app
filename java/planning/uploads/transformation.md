# Transformation plan

## Excepted behavior

### Transformation identity
All transformations are named.
A named can have multiple versions.
A version contains a ser of unique transformation parameters.
The generated variants must know both the name and the version.
The parameters changes are stored like this to avoid writing all parameters to each variant, and to make
migrations easier.

### Updating a transformation
When a named transformation is updated, it gets a new unique version, or marks an older
version as active.
To make sure that that transformation versions are unique, the JSON syntax of the versions of a named transformation must be
updated before attempting to insert a new version.

### Reading
A transformation can be read based on its name, and it returns the parameters of the currently active version.
Using a short near cache on transformations in likely to be beneficial.

## Practical usage

### Upload
The upload request can have eager and incoming transformations. 
Only the transformation name is provided, the media service must get the parameters from the database. 

### Reconciliation
The named transformation are updated in an idempotent upsert-like way.
A given set of parameters is assigned to a name.
The versions are handled automatically.
The main application should have a separate single use server for applying the reconciliation, or
integrate it into an existing server type.
Calling the reconciliation from every node should work in theory, but it is excepted to cause redundant work
at large scale.

### Migration
After a reconciliation causes a difference, the main application can optionally update the variants generated by the previous version of the
given named transformation.
This functionality is excepted to be implemented by the main application by getting the affected uploads from its database and
telling the media service to re-generate the required transformation.
